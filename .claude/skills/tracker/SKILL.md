# Обход списка товаров

## Главный сценарий

**Шаг 1. Для каждого URL из списка вызвать готовый скилл `extract-price`** и
получить от него объект цены `{regular_price, sale_price, has_credit}`.

`tracker` **переиспользует** `extract-price`, а не повторяет его логику. Вся
работа со страницами — адаптеры под магазины, разбор разметки, кодировки,
распознавание антибота, версии API Wildberries — живёт в `extract-price`.
`tracker` подключает его как модуль (`load_extract_price()`) и вызывает
`extract(url, dest)` по одному разу на товар. Своего парсинга здесь нет ни
строки, и заводить его нельзя: два независимых парсера неизбежно разъедутся по
контракту, и таблица начнёт врать.

Практическое следствие: новый магазин добавляется **только** в `extract-price` —
в обходе он заработает сам, без правок в `tracker`.

**Шаг 2. Собрать ответы в единую таблицу прогона** — одна строка на товар:

| Поле строки | Откуда |
|---|---|
| `url` | из списка `TRACKED_URLS` |
| `regular_price` | из объекта `extract-price` |
| `sale_price` | из объекта `extract-price` (`null`, если скидки нет) |
| `has_credit` | из объекта `extract-price` (`null`, если источник не сообщает) |
| `error` | текст ошибки, если снять цену не удалось; иначе `null` |

```
url                                                        regular_price   sale_price  has_credit
-------------------------------------------------------------------------------------------------
https://www.wildberries.ru/catalog/899301731/detail.aspx        65 750 ₽     10 546 ₽         н/д
https://www.wildberries.ru/catalog/200608562/detail.aspx       124 536 ₽     94 896 ₽         н/д
-------------------------------------------------------------------------------------------------
строк: 10 | собрано: 10 | со скидкой: 10 | ошибок: 0 | 2026-09-07T15:27:48+00:00
```

Правила сборки:

- **Одна строка на товар, всегда.** Товар, с которого цену снять не удалось,
  тоже даёт строку — с заполненным `error`. Пропускать его нельзя: иначе по
  таблице не отличить «товар исчез» от «мы его не проверили».
- **`error` в строке всегда.** Он различает `sale_price: null` («скидки нет») и
  `sale_price: null` при непустом `error` («цену снять не удалось»).
- **Порядок строк повторяет `TRACKED_URLS`**, дубликаты отброшены.
- **Поля контракта не переименовываются и не пересчитываются** — в таблицу они
  попадают ровно такими, какими их вернул `extract-price`.

**Шаг 3. Прочитать предыдущий прогон** из `tracker-data` — см. «Сравнение с
предыдущим прогоном».

**Шаг 4. Посчитать изменения** по каждому товару относительно прошлого прогона
и **отбросить незначимые** по правилам из
[`KNOWLEDGE.md`](../../../KNOWLEDGE.md).

**Шаг 5. Закоммитить таблицу** в `tracker-data` через GitHub MCP — см.
«Хранение прогонов».

## Сравнение с предыдущим прогоном

Сравнение делается **до** сохранения нового прогона: иначе файл за сегодняшнюю
дату перезапишет то, с чем нужно сравнивать.

### Как найти предыдущий прогон

1. Получить список файлов в корне репозитория:
   `mcp__github__get_file_contents` с `owner: DmitriyShchikov`,
   `repo: tracker-data`, `path: /`, `ref: main`.
2. Взять **последний по дате** файл `YYYY-MM-DD.json`. Имена в формате ISO
   сортируются лексикографически так же, как хронологически, поэтому достаточно
   выбрать максимальное имя. Файл за сегодня, если он уже есть, — это и есть
   предыдущий прогон: сравнивать нужно с последней снятой ценой, а не с
   позавчерашней. Точное время того прогона лежит внутри файла в `run_at`.
3. Прочитать выбранный файл тем же `get_file_contents`, указав его имя в `path`,
   и сохранить содержимое во временный файл.

**Прошлых прогонов нет — это первый запуск.** Пустой репозиторий отвечает
`409 Git Repository is empty`, репозиторий без файлов прогонов даёт пустой
список. Сравнивать не с чем: сказать об этом пользователю, показать таблицу и
перейти к сохранению. Это не ошибка.

### Как посчитать изменения

```bash
python3 .claude/skills/tracker/scripts/tracker.py --diff /tmp/prev.json
```

Товары сопоставляются **по `url`** — он стабильный ключ, названия у магазинов
плавают. Для каждого сравниваются три поля контракта: `regular_price`,
`sale_price`, `has_credit`.

На выходе — запись на каждый товар:

| `status` | Значение |
|---|---|
| `changed` | хотя бы одно поле изменилось, в `changes` — что именно |
| `unchanged` | все три поля совпали |
| `new` | товара не было в прошлом прогоне |
| `gone` | был в прошлом прогоне, пропал из `TRACKED_URLS` |
| `error` | в одном из прогонов строка с ошибкой, сравнение невозможно |

```json
{
  "url": "https://www.wildberries.ru/catalog/899301731/detail.aspx",
  "status": "changed",
  "changes": {
    "sale_price": {"from": 11200.0, "to": 10546.0, "delta": -654.0, "pct": -5.8}
  }
}
```

Для числовых полей добавляются `delta` и `pct`; для `has_credit` — только
`from` и `to`. `--json` вместе с `--diff` печатает объект `{"run": [...],
"diff": [...]}`.

### Фильтр значимости

Не всякое изменение стоит уведомления. К каждой записи `diff` добавляются поля
`significant` и `signals`; по умолчанию печатаются только значимые записи, а
`--all-changes` показывает и отброшенные.

Правила целиком — в [`KNOWLEDGE.md`](../../../KNOWLEDGE.md), пороги — в
константах `PRICE_MIN_PCT` и `PRICE_MIN_ABS` в начале `scripts/tracker.py`.
Коротко:

- всё считается от **эффективной цены** (`sale_price`, иначе `regular_price`);
- изменение цены значимо, если проходит **оба** порога: не меньше 1% и не
  меньше 50 ₽;
- появление и окончание скидки — по тому же порогу эффективной цены;
- рассрочка: `false` ↔ `true` значимо, переходы через `null` — нет;
- `new`, `gone` и `error` значимыми не считаются.

```
значимые изменения относительно предыдущего прогона
----------------------------------------------------------------------
  899301731
      цена упала: 11 200 ₽ -> 10 546 ₽  -654 ₽ (-5.8%)
----------------------------------------------------------------------
  значимых: 1 | отброшено: 9 (из них 3 с изменениями ниже порога)
```

Почему движение `regular_price` само по себе отбрасывается: на Wildberries это
витринный якорь, магазин двигает его ради процента скидки на карточке. Товар за
17 145 ₽ показывает то «82 528 ₽ до скидки», то «450 000 ₽» — уведомлять об этом
значит слать пользователю маркетинг вместо новостей о цене.

Правила сравнения:

- **Строки с ошибкой не сравниваются.** Отсутствие цены в такой строке означает
  «не смогли снять», а не «цена исчезла»; статус `error`, поля не сверяются.
  Иначе трекер отрапортует о падении цены до нуля из-за таймаута.
- **Переход `null` → значение — это изменение**, но без `delta`: посчитать
  процент от «ничего» нельзя. Так выглядит появившаяся скидка.
- **Сравнивать можно только прогоны с одинаковым `--dest`.** У Wildberries цена
  зависит от региона, и смена региона между запусками даст ложные изменения по
  всему списку.

## Хранение прогонов

Один прогон — один файл в **корне** репозитория `DmitriyShchikov/tracker-data`:

```
tracker-data/
├── 2026-09-05.json
├── 2026-09-06.json
└── 2026-09-07.json     ← сегодняшний прогон
```

- **Имя файла** — дата прогона в UTC, `YYYY-MM-DD.json`. Никаких подкаталогов.
- **Содержимое** — объект из двух полей: `run_at` — точное время прогона в UTC,
  `rows` — таблица прогона из шага 2 (один объект на товар с полями `url`,
  `regular_price`, `sale_price`, `has_credit`, `error`).
- **Повторный прогон в тот же день перезаписывает файл** — за дату остаётся
  последний результат, а прежний виден в истории коммитов. Имя файла даёт только
  дату, поэтому `run_at` внутри и говорит, какой именно прогон записан.

```json
{
  "run_at": "2026-09-07T16:12:42+00:00",
  "rows": [
    {
      "url": "https://www.wildberries.ru/catalog/899301731/detail.aspx",
      "regular_price": 65750.0,
      "sale_price": 10546.0,
      "has_credit": null,
      "error": null
    }
  ]
}
```

Файлы первых прогонов записаны голым массивом, без `run_at`. Скрипт читает оба
формата: `load_run()` возвращает строки и время, а для старого файла время —
`null`.

## Публикация через GitHub MCP

Запись файла через MCP — это **сразу отдельный коммит**. Локальный `git clone`,
`git commit` и `git push` не нужны и делать их не следует: репозиторий
`tracker-data` не клонируется в рабочую директорию вообще.

1. Собрать файл прогона:
   ```bash
   python3 .claude/skills/tracker/scripts/tracker.py --save /tmp/runs
   # файл прогона: /tmp/runs/2026-09-07.json
   ```
2. Проверить, есть ли файл за эту дату в репозитории — нужен его `sha` для
   перезаписи:
   `mcp__github__get_file_contents` с `owner: DmitriyShchikov`,
   `repo: tracker-data`, `path: <YYYY-MM-DD>.json`, `ref: main`.
   Ответ «файл не найден» означает первый прогон за дату — это не ошибка.
3. Закоммитить содержимое файла:
   `mcp__github__create_or_update_file` с параметрами

   | Параметр | Значение |
   |---|---|
   | `owner` | `DmitriyShchikov` |
   | `repo` | `tracker-data` |
   | `branch` | `main` |
   | `path` | `<YYYY-MM-DD>.json` — только имя, без каталогов |
   | `content` | содержимое файла прогона как есть, без base64 (объект с `run_at` и `rows`) |
   | `message` | `Прогон трекера цен за <дата>: N товаров, ошибок M` |
   | `sha` | blob-sha из шага 2; **обязателен**, если файл за дату уже есть |

4. Показать пользователю ссылку на коммит из ответа MCP.

Правила:

- **`sha` обязателен при перезаписи.** Без него GitHub отклонит запись с 422 —
  это защита от затирания чужих изменений, а не сбой скилла.
- **Пустой репозиторий — нормальный случай.** У `tracker-data` может не быть ни
  одного коммита; `get_file_contents` тогда отвечает `409 Git Repository is
  empty`, а `create_or_update_file` создаёт первый коммит на `main` сам.
- **Коммитить только собранную таблицу.** Ничего не дописывать в файл руками и
  не менять форму строк — файл должен читаться теми же правилами, что описаны в
  шаге 2.
- **Прогон с ошибками тоже коммитится.** Строки с `error` — часть истории:
  по ним потом видно, что товар не проверялся, а не подешевел до нуля.
- Если репозитория нет в области видимости сессии, подключить его
  `add_repo` с `access: push`, а не клонировать.

## Когда применять

- «проверь цены», «обнови цены», «собери таблицу по всем товарам»;
- нужна сводка со скидками по всему списку;
- нужна выгрузка в CSV или JSON для дальнейшей обработки.

Одна конкретная ссылка — это `extract-price`, не сюда.

## Быстрый старт

```bash
python3 .claude/skills/tracker/scripts/tracker.py            # таблица
python3 .claude/skills/tracker/scripts/tracker.py --json     # JSON
python3 .claude/skills/tracker/scripts/tracker.py --csv      # CSV
```

Зависимости: `pip install -r requirements.txt`.

Флаги: `--dest <код>` — регион Wildberries (по умолчанию Москва, `-1257786`),
`--delay <сек>` — пауза между запросами (по умолчанию `1.0`), `--full` —
добавить к строке название, размер скидки, наличие и время, `--save <каталог>` —
записать файл прогона `YYYY-MM-DD.json` для публикации, `--diff <файл>` —
сравнить текущий прогон с предыдущим, `--all-changes` — показать и
отброшенные как незначимые изменения.

Коды возврата: `0` — собраны все строки, `1` — часть строк с ошибкой,
`2` — не удалось снять ни одной цены.

## Список отслеживаемых товаров

Список **зашит в теле скрипта** — константа `TRACKED_URLS` в начале
`scripts/tracker.py`. Чтобы добавить или убрать товар, правится этот список:

```python
TRACKED_URLS = [
    "https://www.wildberries.ru/catalog/899301731/detail.aspx",
    "https://www.wildberries.ru/catalog/1498440784/detail.aspx",
    ...
]
```

Дубликаты вычищать вручную не нужно — при обходе они отбрасываются с
сохранением исходного порядка.

## Дополнительные поля (`--full`)

Флаг `--full` добавляет к строке контекст, нужный для отчётов и будущей истории.
Состав строки прогона при этом не меняется — поля только дописываются.

| Поле | Значение |
|---|---|
| `name` | название товара |
| `discount_pct` | считается здесь: `100 − sale ÷ regular × 100`, округление до целых |
| `availability` | `InStock` / `OutOfStock` |
| `checked_at` | время снятия цены, UTC |

## Порядок действий

1. Запустить скрипт. По умолчанию — таблица; для дальнейшей обработки брать
   `--json` или `--csv`, для отчёта с названиями — `--full`.
2. Показать пользователю таблицу и итоговую строку (сколько строк, сколько
   собрано, сколько со скидкой, сколько ошибок).
3. Разобрать строки с `error`, если они есть (см. ниже).
4. Прочитать предыдущий прогон из `tracker-data` и посчитать изменения
   (`--diff`). Если прошлых прогонов нет — сказать, что это первый запуск.
5. Показать значимые изменения. Если их нет — так и сказать: это нормальный
   исход прогона, а не сбой.
6. Сохранить файл прогона (`--save`) и закоммитить его в `tracker-data` через
   GitHub MCP, затем показать ссылку на коммит.

## Разбор ошибок в строках

Ошибка одной строки не прерывает обход — она попадает в колонку `error`, а
остальные товары собираются. Что делать дальше, зависит от текста:

- «товар … не найден» — снят с продажи или опечатка в артикуле. Постоянная
  ошибка: убрать URL из `TRACKED_URLS` или заменить.
- «страница закрыта антиботом», «card.wb.ru недоступен» — временная. Повторить
  позже, список не трогать.
- «нет разметки schema.org» — магазин не поддерживается. Нужен новый адаптер в
  `extract-price`.

## Грабли

- **Пауза между запросами не декоративная.** По умолчанию 1 секунда. Обход без
  паузы выглядит для магазина как наплыв ботов и приводит к блокировке. Снижать
  только для отладки.
- **Сравнивать можно только цены с одинаковым `--dest`.** У Wildberries цена
  зависит от региона (Москва 10 546 ₽ против Санкт-Петербурга 10 388 ₽ на одной
  карточке), поэтому смена региона между запусками даст ложное «цена изменилась».
- **`discount_pct` считается от витринной цены.** На Wildberries `regular_price`
  — маркетинговый якорь (встречается «450 000 ₽ → 17 145 ₽»), поэтому 96% скидки
  в таблице не означают реального падения цены. Для динамики нужна собственная
  история, а не эта колонка.
- **`н/д` в колонке рассрочки — не ошибка.** Wildberries не отдаёт признак
  рассрочки, поэтому `has_credit` там всегда `null`.
